# Phase 4 — IR → Zig Source Emission

## Goal

Take a validated single-file IR and emit a complete Zig source file that, when compiled by `zig build`, produces a `.wasm` artifact implementing the runtime API committed to in `DOCS/decisions/runtime-api.md`. By the end of this phase, the project can take `.circ` source and produce a runnable `.wasm` — the first end-to-end pipeline of the project.

This phase also stands up the *behavioural* test infrastructure: tests that compile the emitted Zig, load the resulting `.wasm` in a runtime, and assert the circuit behaves correctly. These tests use `node` as the WASM host (already a project dependency).

## Scope

In scope:

- A string-templated emitter under `lib/emit/` that produces Zig source from an IR.
- Emission of all 11 runtime exports (`init`, `deinit`, `reset`, `run`, `stop`, `setPin`, `getOutputState`, `getStateSnapshot`, `getTopology`, `getPendingEvents`, `getFileInfo`, `freeBuffer`).
- Emission of `getFileInfo()` data as static Zig constants in `.rodata`.
- Emission of the source-path debug-info table for `getTopology()` (single-file, so paths are shallow — but the table must exist).
- Golden-Zig comparison tests for emitter unit coverage.
- Behavioural tests that compile + run the emitted WASM via `node` and assert outputs.
- A small test harness that wraps "compile this IR, run it, drive these pins, assert these outputs."

Out of scope:

- The CLI subprocess orchestration (`zig build` invocation, temp dirs, `--build-dir` flag). That's Phase 5. Phase 4's tests bypass the subprocess by invoking `zig build` directly against a fixed test harness layout.
- The `@embedFile`-vendored runtime template. The runtime sources used during Phase 4 tests are referenced from their checked-in locations under `lib/`. Phase 5 wraps them in `@embedFile`.
- CLI argument parsing and the three CLI modes. Phase 6.
- Sub-circuit emission (multi-file `buildXxx` chaining). Phase 7. Phase 4 emits only single-file circuits — every component is a primitive.
- Built-in macro library. Phase 8. Phase 4 only knows the primitive set.

## Architectural anchors recap

- Each `.circ` file emits exactly one `buildXxx` function. Sub-circuit instances become call sites — but in Phase 4 there are no sub-circuit instances, only primitives.
- File-info metadata is emitted as static Zig constants, not a JSON blob (Q5 / `decisions/runtime-api.md`).
- Source-path debug info lives outside the engine's `Component` struct, in a parallel debug-info table emitted by the compiler.
- The compiled artifact is pull-based — no `onStateChange` FFI callback in the emitted runtime entry point.
- String-templated emission (Q7a, decision (i)).

## Emitted file structure

The emitter produces a single Zig file (`compiled.zig` per Q8b). High-level shape:

```zig
//! Generated by circ-compile. Do not edit.
//! Source: <path>
//! Compiled at: <timestamp>
//! Compiler version: <version>

const std = @import("std");
const engine = @import("circuit.zig");

// === File info (static, exposed via getFileInfo) ===
const file_info_blob: []const u8 = ... ;  // packed binary or text

// === Source-path debug table (static, exposed via getTopology) ===
const debug_paths: []const DebugPath = &.{ ... };

// === Circuit construction ===
fn buildCircuit(circuit: *engine.Circuit) !struct {
    pin_<name>: *engine.Component,        // one field per input pin
    output_<name>: *engine.Component,     // one field per output pin
    led_<name>: *engine.Component,        // one field per LED (for snapshot indexing)
} {
    const pin_a = try circuit.createComponent(.{ .input_pin_gate = .{ ... } });
    const not_g = try circuit.createComponent(.{ .not_gate = .{ ... } });
    try circuit.connect(pin_a, "out", not_g, "in");
    // ...
    return .{ .pin_a = pin_a, ... };
}

// === Runtime state ===
var arena: std.heap.ArenaAllocator = undefined;
var circuit: engine.Circuit = undefined;
var components: ComponentTable = undefined;  // ComponentId → *Component

// === WASM exports ===
export fn init() void { ... }
export fn deinit() void { ... }
export fn reset() void { ... }
export fn run() void { ... }
export fn stop() void { ... }
export fn setPin(component_id: i32, state: i32) void { ... }
export fn getOutputState(component_id: i32) i32 { ... }
export fn getStateSnapshot() callconv(.C) PtrLen { ... }
export fn getTopology() callconv(.C) PtrLen { ... }
export fn getPendingEvents() callconv(.C) PtrLen { ... }
export fn getFileInfo() callconv(.C) PtrLen { ... }
export fn freeBuffer(ptr: [*]const u8, len: usize) void { ... }
```

The exports' bodies are largely fixed boilerplate — the *only* circuit-specific code is `buildCircuit` and the static blobs (`file_info_blob`, `debug_paths`, the component table layout). Most of the emitter's complexity is in `buildCircuit` and the static data.

## Emitter organisation

Emission is split into focused modules:

- `lib/emit/writer.zig` — a thin wrapper around `std.io.Writer` with helpers for emitting Zig identifiers (escaping reserved words), string literals (escaping), and indented blocks.
- `lib/emit/build_fn.zig` — emits the `buildCircuit` function from the IR's components and connections.
- `lib/emit/file_info.zig` — emits the static file-info blob.
- `lib/emit/debug_paths.zig` — emits the source-path debug table. In single-file mode, every path is `[<root_name>, <instance_name>]` — flat, but the table must exist for `getTopology()` to work.
- `lib/emit/runtime.zig` — emits the runtime exports and state. Largely static text with a few interpolation points (the kind id of `init_pin` for `setPin`'s validation, the count of components for the snapshot allocator, etc.).
- `lib/emit/main.zig` — top-level entry point that calls each sub-emitter in order and stitches the output.

## Behavioural test harness

A new helper at `tests/helpers/wasm_run.zig` (or a sibling `.js` file invoked from Zig) provides:

```
fn compileAndRun(
    ir: *const Ir,
    script: []const u8,                  # JS snippet that drives the wasm and prints results
) ![]const u8                            # captured stdout
```

Implementation:

1. Emit Zig source from the IR to a temp dir.
2. Run `zig build` against a fixed test-harness `build.zig` in that dir, producing `compiled.wasm`.
3. Spawn `node` with a small loader script that loads `compiled.wasm`, executes `script`, and prints results to stdout.
4. Capture stdout, return.

The `script` is a JS snippet calling exports like `setPin(2, 1); run(); console.log(getOutputState(5))`. Tests assert on the captured stdout.

The test-harness `build.zig` is a separate file from the production `build.zig` template — Phase 5 owns the production template. Phase 4's harness is the simplest thing that compiles the emitted source against the engine in `lib/`.

## Slices

### Slice 4.1 — Writer + buildCircuit emission

**What ships.** `lib/emit/writer.zig` and `lib/emit/build_fn.zig`. Given an IR, emits just the `buildCircuit` function (no exports yet, no static blobs). The output is a Zig snippet that's not yet a complete file.

**Tests.** Golden-file tests:

- `tests/fixtures/circuits/<name>.circ` (reusing fixtures from Phase 2/3) → run through Phase 2's parser + resolver + Phase 3's validator (must come back clean) → through `build_fn` emitter → compare to `tests/fixtures/expected-zig/<name>_build_fn.zig`.

Coverage:
- Single primitive (input → led).
- Multiple primitives connected.
- Component instance names containing characters that need Zig escaping.
- Anonymous components (auto-generated names from Phase 2).

**Files touched.** `lib/emit/writer.zig`, `lib/emit/build_fn.zig`, fixtures.

### Slice 4.2 — File info and debug paths

**What ships.** `lib/emit/file_info.zig` and `lib/emit/debug_paths.zig`. Each emits its respective static blob given an IR. The encoding format for both blobs is decided here and locked — the runtime exports (next slice) read them.

**Tests.** Golden-file tests for each emitter independently. A round-trip test: emit the file-info blob, parse it back with a small Zig decoder (which the runtime exports also use), assert the round-tripped value matches the input.

**Files touched.** `lib/emit/file_info.zig`, `lib/emit/debug_paths.zig`, `lib/emit/file_info_format.zig` (the shared encode/decode helper used by both the emitter and the runtime exports), fixtures.

### Slice 4.3 — Runtime exports emission

**What ships.** `lib/emit/runtime.zig` emits the WASM-export functions. Most of this is fixed text; the per-circuit interpolation points are: the `setPin` validation table (which component IDs are valid input pins), the component count (for snapshot allocation), and the names of the static blobs to expose.

`lib/emit/main.zig` stitches everything together: header comment, imports, `buildCircuit`, static blobs, runtime state, exports.

**Tests.** Golden-file test for the full emitted file. Reuses the Phase 2/3 fixtures and pairs them with `tests/fixtures/expected-zig/<name>.zig` (the complete file, not just `_build_fn` snippets).

**Files touched.** `lib/emit/runtime.zig`, `lib/emit/main.zig`, fixtures.

### Slice 4.4 — Behavioural test harness

**What ships.** `tests/helpers/wasm_run.zig` and a fixed `tests/harness/build.zig` that knows how to compile emitted Zig against `lib/circuit.zig`. Plus a small `tests/harness/loader.js` that `node` executes to load and drive the compiled WASM.

The harness creates a temp dir, drops `compiled.zig` (the emitted source) and a copy of the engine sources into it (or references them via path — pick whichever works with Zig's module system), runs `zig build`, then spawns `node` with the loader script.

**Tests.** A single end-to-end test that:
- Takes the simplest fixture (e.g. an inverter: `input → not → led`).
- Compiles it through Phase 2 → Phase 3 → Phase 4.
- Runs it through the harness with a JS snippet: `setPin(input_id, 1); run(); console.log(getOutputState(led_id))`.
- Asserts the captured stdout is `"0"` (NOT-of-1 = 0).
- Repeats with input=0, asserts stdout is `"1"`.

This single test proves the entire pipeline works end-to-end. It's the first phase where that's true.

**Files touched.** `tests/helpers/wasm_run.zig`, `tests/harness/build.zig`, `tests/harness/loader.js`.

### Slice 4.5 — Behavioural fixtures

**What ships.** A set of behavioural fixtures, each pairing a `.circ` source with an expected behaviour spec. The spec format is a small Zig struct or a parallel `.txt` file describing pin-setting sequences and expected outputs:

```
# tests/fixtures/expected-wasm/and_gate.txt
# Format: <inputs as space-separated pin=state> => <outputs as space-separated pin=state>
a=0 b=0 => out=0
a=0 b=1 => out=0
a=1 b=0 => out=0
a=1 b=1 => out=1
```

The harness from slice 4.4 runs each fixture's input sequences and asserts on outputs.

Initial fixtures:
- `inverter.circ` — single NOT.
- `and_gate.circ` — single AND with two inputs, full truth table.
- `and_of_not.circ` — `pin1 AND (NOT pin2)`, full truth table.
- `chain.circ` — three NOTs in series, verify timing/settling.
- `unused_input.circ` — clean fixture with `W001` warning, behaviour still correct.

**Tests.** Each fixture is its own `test "..."` block invoking the harness.

**Files touched.** `tests/fixtures/circuits/<name>.circ`, `tests/fixtures/expected-wasm/<name>.txt`, a Zig test file that loops over the fixture pairs.

## Definition of done for Phase 4

- All five slices committed.
- `zig build test` passes (including the new behavioural tests, which require `node` on the PATH — document this in `tests/README.md`).
- The full pipeline `.circ` → AST → IR → validation → emission → `zig build` → `.wasm` → `node` execution works for single-file circuits using only primitives.
- All 11 runtime exports are emitted and tested at least once via the behavioural harness.
- Golden-Zig fixtures cover every emitter sub-module.

## Open questions to resolve at slice time

- The encoding format for `file_info_blob`. Two options: a Zig-readable struct literal in the emitted source (`const file_info = .{ .name = "...", .inputs = &.{...}, ... }`) versus a packed binary blob with a length prefix. Recommendation: struct literal — emitted code is already Zig, and the runtime export can return a pointer into it directly. Binary packing is over-engineering for static data.
- The debug-paths encoding. Same recommendation: struct literal.
- How `tests/harness/build.zig` handles engine source dependencies. Two options: (a) symlink/copy the engine files into the temp dir, (b) use Zig's `addModule`/`addImport` to reference them in place. (b) is cleaner but requires the test harness `build.zig` to know the path back to the repo's `lib/`. Pick (b); the production template (Phase 5) will use `@embedFile` instead.
- Whether `getStateSnapshot`, `getTopology`, `getPendingEvents` allocate buffers on each call or reuse a pre-allocated one. Allocate per call for correctness; the host frees via `freeBuffer`. Reuse can be revisited if profiling shows allocation cost.
- Component-table representation in the emitted code. A simple array indexed by `ComponentId` (which is sequential from 0) is fine. No need for a hash map at this layer.

## Notes for the next phase

Phase 5 wraps the emitter and the harness build into the actual CLI build flow: it `@embedFile`s the runtime template (the engine sources + a production `build.zig`), creates a temp dir, drops the embedded files plus the emitted `compiled.zig`, shells out to `zig build`, and copies the resulting `.wasm` to the user's `-o` path. The emitter and the engine don't change in Phase 5 — only the orchestration around them.

The behavioural test harness from slice 4.4 stays in use through the rest of the project. Phase 5 adds *additional* end-to-end tests that exercise the subprocess + temp-dir path; Phase 4's harness is the in-process shortcut.
