# Plan Prompt — Canvas theme (the site's circ-renderer skins, upgraded to the v2 asset set)

## What Is Being Built

The docs site draws every live circuit through one theme module, `site/src/utils/circ-theme.mjs` (710 lines): two 24-key palettes, ten skins, a wire painter, a transparent background, a no-op port marker and a highlight hook, all handed to the pinned `circ-renderer` by `site/src/components/LiveCanvas.astro` and `site/src/components/Playground.astro` at `cell = 14`. A design handoff under `DOCS/design/` (README, `circ-site-theme.js`, the interactive sheet `Circ Renderer Assets - Site Theme.dc.html`) audited that theme against the renderer and found ten gaps, nine of them defects: an 8-bit bus draws in plain green because `wireRenderer` and `drawTailLine` never consult `wireStyleOf` for colour and neither palette defines `wireBus` or `busLabel`; every stroke is a hardcoded `lineWidth = 4` (`circ-theme.mjs:144`, `:655`) so wires are hairlines at `cell = 24` and swamp the sprites at `cell = 10`; the NOT label is drawn with `yOffset = -cell * 15` (`circ-theme.mjs:440`) and lands inside the sprite; the PNG gates are static, so a HIGH and a LOW gate differ only in tail colour; the same dark-interior PNGs composite onto the lavender light pane; dark-mode `wireIdle` is `#dee2e6`, the brightest thing on a `#0c0517` pane, so idle wires out-shout active ones; the renderer's fan-out dot has no theme hook and is stamped in the wire's own colour on top of the wire (`circ-renderer/src/render/canvas.ts:845-881`); and hover swaps the pin's fill for yellow, hiding the value about to be toggled. The handoff then designs the upgrade in the same language (orange is HIGH, green is LOW, blue is output, purple is macro) and extends it to the full ANSI gate family, a slice ruler and concat bands, a two-faced subcircuit chip, and ROM/RAM chips that show the addressed word.

This initiative ports that design into the site and the renderer. The port target is `DOCS/design/circ-site-theme.js`: its `nextSiteDark` / `nextSiteLight` palettes (28 keys: the 24 plus `surface`, `spriteInk`, `wireBus`, `busLabel`, minus the dead `grid`), its `nextSiteSkins` table, `drawWireNextSite`, and the three caches (`tintCache`, `haloCache`, `boundsCache`). The renderer grows the three small things the design needs and the theme cannot supply from outside: a `fanOutMarker` hook beside `wire` and `portMarker`, rounded corners in `traceWire`, and a row gutter the host can widen. The compiler does not change: no new component kinds, no new runtime export. Builtin gates reach the canvas as collapsed macro boxes (`LiveCanvas.astro` passes no `layoutOptions`, so `collapse.ts` groups each `or`/`nand`/`xor` instance into one subcircuit node), and the design's `subcircuit` skin already draws those through the gate recipe on a virtual 5-wide box; the RAM write indicator is derived on the canvas from the same edge rule the engine applies (`lib/circuit.zig:196-199`), and the exact runtime stamp the handoff asks for is deferred.

**Definition of done.** Every `<LiveCanvas>` on `/`, `/gallery` and the tour, and the simulation pane of `/playground`, draw with the upgraded theme in both `data-theme` modes and at `cell` 10, 14 and 24; each of the nine defects above is closed and the tenth (hover) is a ring outside the pin; `site/src/utils/circ-assets.mjs` carries only the `AND` and `OR` sprites; the site pins a `circ-renderer` sha whose `bun test` and `tsc --noEmit` are green and whose README documents the three additions; `bun test`, `bun --bun run typecheck`, `bun --bun run build` and `bun run bundle` are green in `site/` with no ceiling raised; `zig build test` is untouched because no Zig file changed; `DOCS/decisions/canvas-theme.md` records the decisions each phase exercised; and the human has reviewed the gallery once per phase in light and dark.

Scripts: `bun run libcirc`, `bun run scripts/compile-content.ts`, `bun run bundle` (`site/scripts/check-bundle.ts` against `site/bundle-budget.json`: `default` 10 KB gzip, `/playground` 120 KB gzip).

Its `test/canvas-stub.ts` is the headless 2D context the canvas tests use.

## Architectural Constraints

- **The renderer's hook model stays; the site fills hooks, it does not reach around them.** Every mark the site draws goes through a `CircTheme` member (`skins`, `wire`, `portMarker`, `busValue`, `highlight`, `background`, and the new `fanOutMarker`). A drawing the design needs and no hook allows is a renderer slice first, never a site workaround that repaints over the canvas's own marks.
- **The `LayoutGrid` contract is frozen and the parity harness is untouched at default options.** Footprints (`sizing.ts`: pins `max(5, name+4) × 3`, gates `5×5` and `5×3`, slice `max(5, label+2) × 3`, concat `5 × (2n+1)`, macro `max(8, label+2) × (2n+1)`, memories `max(5, label+4) × 3 | 9`) and port tables do not move; the design was authored on them (`DOCS/design/circ-scenes.js`). The wider row gutter the value pill needs is a `LayoutOptions` field with default `1`, so `test/layout-parity.test.ts` and the Zig conformance goldens (`tests/fixtures/preview/layouts-json/`) see no change.
- **The compiler is read-only.** No kind byte in `lib/topology/format.zig` (the language locks `or`/`nand`/`nor`/`xor`/`xnor` as auto-imported macros, `DOCS/decisions/language.md`), no `buffer`, no new runtime export in `templates/main.zig`. The handoff's "new kinds needed in the library" paragraph is superseded by decision 4 below; its "runtime ask" for the write flash by decision 11.
- **One ring, drawn by the canvas.** `DOCS/decisions/playground.md` ("The renderer exposes three host hooks, and the highlight reuses `hovered`") and `site/test/circ-theme-hover.test.ts` fix that the highlight ring is drawn once, through the `highlight` hook, for every kind, and no skin draws its own. The design's pin ring lands inside that hook (a circle for pins, the rounded rectangle for everything else); `nsHoverRing` is not called from a skin.
- **The site's `wire` hook traces through the renderer.** Today's `wireRenderer` calls `traceWire` so the site cannot draw a jump anywhere the renderer would not (`circ-theme.mjs:659`). Rounded corners therefore land in `wire-path.ts` as an option, not as a second path builder in the site.
- **The canvas stays transparent.** `background` keeps `clearRect` (`circ-theme.mjs:685`); nothing fills with `background`; the fan-out knock-out uses `destination-out` as the design specifies.
- **Every stroke and font is cell-relative.** No literal pixel width survives except the `max(…)` floors the design states (`max(2, cell × 0.16)` wire, `max(2, cell × 0.28)` LED stroke, `max(1.5, cell × 0.1)` chip stroke). A source-text test asserts no `lineWidth = <number>` remains.
- **Caches are keyed on stable ids.** `tintCache`, `haloCache`, `boundsCache` key on the sprite's name and the colour, never on `img.src.slice(-20)`; `shadowBlur` runs only when a halo is first rendered offscreen, never per frame (`nsVecHalo` and `haloSprite` in the design file; `nsGlow` is an oversize translucent under-pass, not a blur).
- **Behaviour a `bun test` can reach lives in a module without module-scope side effects.** `circ-theme.mjs` calls `loadAssets()` at import (`:34`), which is why today's test is a source-text guard. The theme splits so palettes, geometry helpers and skins take sprites by injection and can be driven under `bun test` with a recording context; the `.astro` islands stay thin.
- **The JavaScript budget is per page and never raised silently** (`DOCS/decisions/playground.md`). The theme chunk is reached only through `import()` from `LiveCanvas.astro:69` and `Playground.astro:2785`, so it is reported, not gated; it is still measured in STATUS before and after the sprite removal.
- **Documentation lands with the code.** Each phase appends its exercised decisions to `DOCS/decisions/canvas-theme.md` (registered in `DOCS/decisions/index.md`); the renderer README's theme section gains the three additions in the phase that ships them; `DOCS/design/README.md` is not edited (it is the handoff, not our doc).
- **Git conduct per `CLAUDE.md`:** stage by path, Conventional Commits under 70 characters (scopes `site`, `renderer` for the second repository), no phase or slice prefixes, no trailers, never push; the renderer is a second repository with the same rules and its push is the human's, exactly as the layout and playground plans gated it.

**Locked decisions.** Routine calls made at plan time so no slice reopens them. Each phase appends the ones it exercises to `DOCS/decisions/canvas-theme.md`.

1. **The port target is the JS file, not the README.** Where `DOCS/design/README.md` and `circ-site-theme.js` disagree, the code wins and STATUS names the value taken. Two known disagreements: the corner radius (README `cell × 0.4`; `drawWireNextSite` uses `cornerR = cell * 0.6`) and the hover ring offset (README `r + 0.32`; `nsHoverRing` uses `r + cell * 0.38`).
2. **The palettes are `nextSiteDark` / `nextSiteLight` verbatim** (`circ-site-theme.js:395-455`): `surface` (`#160b26` / `#ffffff`), `spriteInk` (`#e8ddff` / `#8672b5`), `wireBus` (`#bea7ff` / `#6e49ab`), `busLabel` (`#0c0517` / `#ffffff`) added; `labelOnComponent` dark flips to `#0c0517`; `wireIdle` dark drops to `#4c3a6b`; `grid` deleted from the site palette. `PaletteKey` (the JSDoc typedef over `colorsDark`'s keys) follows, so `CircView<PaletteKey>` in both islands types the new set.
3. **Three renderer additions, one pin bump.** (a) `CircTheme.fanOutMarker?: (args: FanOutMarkerContext) => void` with `{ ctx, theme, cell, x, y, value, signal }`, called from `drawFanOutMarkers` in place of the hardcoded dot; (b) `traceWire` and `wirePath` take an options object `{ arcRadius?, cornerRadius? }` (the positional `arcRadius` stays accepted), rounding every corner with `arcTo` and splicing crossing hops into the same continuous path as `drawWireNextSite` does; (c) `LayoutOptions.rowGutter?: number` (default `1`) threaded into `coords.ts` where `ROW_GUTTER` is read (`:110`, `:135`). `grid` leaves `ThemeColorKey` and `defaultColors`; the README's colour table follows. All three ship in Phase 0 as one renderer branch the human pushes once; `RENDERER_PIN_VERSION` bumps to the package version that branch declares.
4. **No new component kinds.** The six two-input builtins draw through the `subcircuit` skin's recipe table (`circ-site-theme.js:976-994`) on a virtual 5-wide box centred in the macro box, tails running to the real ports (`portsFrom`), in opaque mode; in expanded mode (the playground's "Expand macros" setting, `Playground.astro:179`) they are the `and`/`not` primitives they are made of, drawn by the primitive skins. `BUFFER` has no source form and is not drawn. The recipe keys stay lowercase names as `collapse.ts` reports them.
5. **Only `AND` and `OR` sprites remain.** `NAND`, `XOR` and `NOT` leave `circ-assets.mjs` in the phase that stops reading them (Phase 3); NOT and the negated gates are the base silhouette plus the standard bubble; the size of the removed base64 is recorded in STATUS.
6. **Sprites are tinted, measured and haloed once per (sprite, colour).** `tintSprite`, `haloSprite` (`HALO_PAD = 0.18`, alpha `0.55`) and `spriteBounds` (one `getImageData` over the 128×128 sprite) are ported as written; the symbol is sized by painted bounds so the lobes span the port rows. The data-URI sprites are same-origin, so `getImageData` does not taint.
7. **The value pill is drawn by the `busValue` hook for every bus, and by the pin skin for a single bit.** The canvas calls `busValue` only for `bitWidth > 1` (`canvas.ts:821`) and hands it `text` already spelled in the reader's `valueFormat` (hex, binary or decimal, a playground setting reached through `setValueFormat`); a skin has no access to that format, so a bus pill drawn from a skin would ignore it. The hook therefore draws `nsValuePill` in `wireBus` / `busLabel` above every multi-bit component except `rom` and `ram` (their word is in the body), seated at `cy − r − 0.5 cell` for pins and at `y − 0.5 cell` for boxes; the `input_pin` and `output_pin` skins draw the `0` / `1` / `?` pill themselves only when `bitWidth === 1`. No off-palette `#1971c2` text remains.
8. **The row gutter is 2 on the site, by option, and the padding follows.** With the pin radius `min(w,h)/2 − 0.08 cell = 1.42 cell` and the pill seated `0.5 cell` above it, the pill's top is `1.34 cell` above the box: it overlaps a box directly above by `0.34 cell` at `ROW_GUTTER = 1`, and at `cell = 14` the islands' `padding = 16` (`1.14 cell`) clips a top-row pin's pill by about 3 px. Both islands pass `layoutOptions: { rowGutter: 2 }` and `padding = Math.ceil(cell * 1.5)`. The ASCII preview and the Zig side keep `ROW_GUTTER = 1`; the two media already differ in everything but the grid, and the parity harness runs at default options.
9. **Hover is a ring, drawn by the highlight hook, and the pin keeps its state.** The `highlight` hook draws a circle at `r + 0.38 cell` in `inputHover` for `input_pin` and `output_pin`, and the existing rounded rectangle for every other kind (the editor highlight of a `rom` from `source-link.ts` must still light up). `drawInputPin`'s fill swap on `hovered` is removed; `circ-theme-hover.test.ts`'s "the input pin reacts to hovered" case is rewritten to assert the opposite.
10. **The RAM write indicator mirrors the engine's edge rule on the canvas.** The engine writes on `clk` rising (`bit0High(now) and bit0Low(prev_clk)`) with `we` high and `addr` fully defined, and its initial `prev_clk` is undefined so the first defined-high clock is not an edge (`lib/circuit.zig:196-206`, `:477-479`). The `ram` skin keeps one `prev_clk` per `(canvas, component id)` in a `WeakMap` keyed on `ctx.canvas`, evaluates the same predicate over `inputValues` (`addr`, `din`, `we`, `clk` in port order) on each draw whose inputs changed, and lights `wr ●` for the draw in which it fires. This is an indicator, not a proof: a `we` that settles low in the same step the clock rises can differ from the engine. The exact stamp is decision 11.
11. **The runtime write stamp is deferred, not smuggled in.** The exact signal would be a `last_write_time` on `MemoryState`, one export beside `getMemInfo` in `templates/main.zig`, and a `CircRuntime` accessor: four layers and a new runtime for every artifact, for one dot. It is recorded here and in `DOCS/decisions/canvas-theme.md` as the follow-up if the mirrored rule proves misleading in the gallery review.
12. **The addressed word is `outputValue`, the address is `inputValues[0]`.** Reads are asynchronous (`memoryReadOut` on every recalc, `lib/circuit.zig:217`), so the body's `addr → word` needs no runtime access from a skin; `?` when either is not fully defined. Header: mode left, `W×2^A` right, from `component.bitWidth` and `component.memory.addrWidth`.
13. **A slice wider than 16 bits shows a range bar, not a ruler.** The handoff leaves this undesigned ("above ~16 bits the ruler should collapse to a range bar — not designed yet"). The rule here: up to 16 input bits draw the ruler; above that, one bar with the tapped span filled in `wireBus` and the `[lo:hi]` label under it. The deep planner may refine the bar; it may not exceed the slice footprint.
14. **The theme module splits into three files.** `site/src/utils/circ-palette.mjs` (the two palettes, `PaletteKey`, `pickPalette`), `site/src/utils/circ-skins.mjs` (every skin, the wire, marker and hook functions, the three caches; sprites and `document` reached through an injected `assets` object so `bun test` can pass a stub), and `circ-theme.mjs` kept as the entry the islands import (`blogTheme`, `blogThemeLight`, `pickTheme`, `onAssetsReady`, `blogAssetsReady`), so `LiveCanvas.astro` and `Playground.astro` change only for the padding and layout options of decision 8.
15. **Tests are a recording context plus source-text guards.** `site/test/circ-skins.test.ts` drives every registered skin through a Proxy context modelled on `circ-renderer/test/canvas-stub.ts` at `cell` 10, 14 and 24, signals 0, 1 and 2, widths 1 and 8, asserting: `save`/`restore` balance, no `lineWidth` below the design floors, every `fillStyle`/`strokeStyle` a palette value (no literal hex outside the palette file), `setLineDash([])` after every dashed stroke, and `globalCompositeOperation` restored after `destination-out`. `circ-theme-hover.test.ts` is updated, not deleted. The human's gallery review at the end of each phase is the visual gate; a phase is not shipped until STATUS records it.
16. **The handoff bundle is tracked, minus the noise.** Phase 0 commits `DOCS/design/{README.md,github.md,circ-site-theme.js,circ-skins.js,circ-scenes.js,support.js,*.dc.html}`; `.DS_Store` files and `DOCS/design/site/src/utils/circ-assets.mjs` (byte-identical to the site's) are not committed. When the initiative archives, `DOCS/design/` moves to `DOCS/archive/design/canvas-theme/` so the archive prompt's highlight view can point at it.

**Explicitly deferred, and not to be smuggled into a slice:** new component kinds (`buffer`, `or_gate`, `nand_gate`, `nor_gate`, `xor_gate`, `xnor_gate`) in the compiler, the renderer or the site; the runtime write stamp (decision 11); a redesign of the range bar beyond decision 13; changes to footprints, port tables or `ROW_GUTTER` in the Zig preview; the renderer's own default theme and skins (`defaultSkins` stay as they are; the library sheet `Circ Renderer Assets.dc.html` is context only); animation or transitions; the library's `ThemeColorKey` set beyond removing `grid`.

## Working Loop

The execution agent follows this loop every session without exception:

### On Cold Start

1. Read this file (`DOCS/PLANS_PROMPT.md`) in full.
2. Read `DOCS/STATUS.md` (if it exists). The latest entry defines what was last shipped and what comes next.
3. Run `git log --oneline -10` and `git status` in this worktree, and the same in `~/circus/circ-renderer` when the slice touches it. If STATUS claims a slice is committed but it does not appear in `git log`, the human has not committed yet — **do not begin a new slice**. Stop and say so.
4. Read the active phase plan (`DOCS/PLANS/PHASE_<N>_<name>.md`) for the current phase.
5. Implement the next slice per the phase plan. Do not start a second slice until the first is reviewed and committed.

### Each Slice

1. Implement the full slice as specified. Do not stop mid-slice.
2. Run the gates for what the slice touched: `bun test`, `bun --bun run typecheck`, `bun --bun run build`, `bun run bundle` in `site/`; `bun test` and `bunx tsc --noEmit` in `circ-renderer`. Do not ship a slice that breaks a suite.
3. Append a STATUS entry (template below).
4. Stage the slice's files (`git add <files>`), by path, in the repository they belong to.
5. Display the proposed commit message and **stop**. Wait for explicit human approval before running `git commit`. Do not begin the next slice until the commit is confirmed and made.

### Git Rules

- Read-only git commands (`status`, `log`, `diff`) are encouraged for situational awareness.
- **Committing:** At the end of a slice — and only at the end of a slice — the agent stages the slice's files (`git add <files>`), then displays the full proposed commit message to the human and waits for explicit approval before running `git commit`. Staging first lets the human inspect the diff in any git client before approving. Do not commit without that confirmation.
- Do **not** push, force-push, amend, rebase, reset, delete branches, or run any other write `git` or `gh` command under any circumstances. The renderer's push and the `bun add circ-renderer@github:jeffersonmourak/circ-renderer#<sha>` that follows it are the human's.

**Renderer and pin**

- The site's `renderer-pin.test.ts` reads `node_modules/circ-renderer/package.json` and `bun.lock`; a `bun add` that rewrote one but not the other fails there, not at runtime. Bump `RENDERER_PIN_VERSION` in the same slice as `package.json`.
- The renderer's `draw()` order is fixed (`canvas.ts:703-766`): skins are drawn before fan-out dots, port markers and bus badges, and the highlight is last. A skin cannot draw "on top of" the pill of another component; only the hooks that run later can.
- `SkinContext` has no runtime handle. A skin that needs state across draws (the RAM `prev_clk`) keeps it in a module-level `WeakMap` keyed on `ctx.canvas`; `setTheme` swaps the theme without rebuilding the canvas (`canvas.ts:194`), so the map survives a theme flip and is dropped with the element.

**Site tests**

- `bun test` has no `Image`, no `document` and no `HTMLCanvasElement`. Anything that touches them at module scope makes the whole module untestable; keep them behind the injected `assets` object of decision 14.
- `circ-theme-hover.test.ts` matches source text (`const <name> = (`, `\n};\n`, `const skins = {`). Renaming or reformatting a skin can break it without a behaviour change; update the guard in the same slice.

**Drawing**

- `destination-out` and `setLineDash` leak into everything drawn after them unless restored; the recording-context test asserts both, and every helper wraps them in `save`/`restore`.
- `spriteBounds` runs `getImageData` once per sprite; do it on the decoded image from `loadAssets()`, never on a tinted copy, or the bounds change with the colour.
- The design's `nsFont(cell, weight)` sizes text by `cell`; the renderer's `theme.font` (`'600 11px …'` today, `circ-theme.mjs:677`) is a fixed size that the library's default bus badge and `drawLabel` read. Once the site's `busValue` hook draws every badge, `font` is unused by the canvas for the site; keep it defined anyway, as the renderer types it optional and the dialog reads `theme.colors` only.

**Budget**

- The theme chunk is lazy on every route (`import('../utils/circ-theme.mjs')`) and so is reported, not gated, by `bun run bundle`; it still shows up as an ungated line, and the sprite removal in Phase 3 should make that line smaller, not larger. Record both numbers.
