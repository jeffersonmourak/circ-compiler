Four new keys: surface (the fill inside hollow pins, chips and shells), spriteInk (what LOW gate art is tinted to), and the two the library already expects, wireBus and busLabel. One semantic flip: dark-mode labelOnComponent goes from white to the pane color, because white on #fd7e14 is 2.9 : 1 and dark ink is 7.6 : 1. grid is carried but is dead in both themes — canvas.ts never reads it.

24 keys against the library's 14, and only 12 are shared. Twelve are site-only — inputOn/Off, inputBorderOn/Off, outputOn/Off, outputBorderOn/Off, portOn/Off, inputHover, labelOnComponent — and two of the library's, wireBus and busLabel, missing entirely. Semantics differ from the default theme: orange is HIGH, green is LOW, blue is output.

07 — Proposed upgrade

same language, eleven changes

Nothing here abandons the site's identity. Orange still means HIGH, green still means LOW, blue still means output, the gate art is still your PNGs. What changes is that state stops being carried by color alone, buses get a treatment they never had, and the two parts that fell through to the library now speak the same visual language as everything else.

08 — The rest of the gate set

ANSI silhouettes, composed not redrawn

The library ships two gates. The site's sprite map quietly adds three more, but only as builtin subcircuits — they have no ComponentKind of their own. Three are missing outright. Every gate is authored from three containers laid out inside the same box — port · [exclusive] [gate] [negate] · port. All three slots are always reserved, so the symbol is the same size and sits at the same x across the whole family, and the box, ports and tails never move. AND, OR and BUFFER use only the gate slot; NAND, NOR and NOT add the negate bubble; XOR adds the exclusive curve to OR; XNOR uses all three. Only two sprites remain in play — AND and OR — plus one vector triangle.

▢ exclusive · 0.55 cell · stroked arc nested in the OR back, same depth ▢ gate · symbol sized once from the port spread and the gate-slot width, by its painted bounds ▢ negate · 0.55 cell · bubble r 0.24, tangent to the measured tip inset from box edge · 0.4 cell · empty slots only recentre the symbol, never resize it

Landing these means four edits per gate: a kind byte in format.zig, a ComponentKind entry in topology.ts, a footprint in primitiveSizing, and port slots in resolvePortCoords. All six two-input gates reuse the AND footprint (5 × 5, ports a at y+1, b at y+3, out at y+2); BUFFER reuses NOT's (5 × 3).

09 — Slice & concat

draw the bit field, not a box around a label

Slice is a ruler of the incoming word, MSB on the left so it reads in the same direction as the hex badge above it. The tapped bits are filled in the bus color, the discarded ones left hollow. You can see [0:4] takes the low nibble without decoding the notation.

Concat is the assembled word: one band per operand stacked in bit order, with a numbered lane running in from each port. Operand 0 sits at the top and fades downward, so which input lands where is visible rather than implied by port order.

{{ bp.name }} {{ bp.note }}

Both keep their existing footprints — slice max(5, label+2) × 3, concat 5 × (2n+1) — so nothing in place.ts moves. Slice reads its incoming width from inputValues[0].width, which the skin context already provides; above about 16 bits the ruler would need to collapse to a range bar.

10 — Subcircuit

two faces, one part

Builtin macros (and, nand, or, xor, not) borrow the gate assets from section 08 — same three containers, same sizing, same halo — so a macro reads as the gate it is. The instance name goes below, in the same muted label as every other part.

User subcircuits get a chip: a macro-purple shell with a tinted header band carrying the subcircuit name in caps, and the instance name in the body. The header is what separates "a box I wrote" from the gate family at a glance; the body is where the instance is identified. Height grows with input count as it does today.

{{ sub.name }} {{ sub.note }}

Footprint unchanged: max(8, label+2) × (2n+1). Tails and terminal dots follow the same rule as the gates — inset 0.4 cell, dot at inset − 0.4 — so a macro sits on the wire exactly like a primitive. Bus-width ports pick up the bus color on their tails.

11 — ROM & RAM

circ-compiler PR #79 · branch memories

Both take the subcircuit chip. The header carries the declaration — mode on the left, W×2^A shape on the right — because contents are runtime configuration and the shape is the only thing the source knows. The body shows the one thing a reader wants from a memory mid-simulation: the addressed word, addr → word, word in the bus color. An unloaded cell reads ? like any undefined value.

ROM is one port in, one out, three rows — the instance name goes below like a pin. RAM stacks addr · din · we · clk on the odd rows of a nine-row box, labels them inside the left edge, and adds a write indicator in the corner that lights orange on the we·clk edge — the only moment a RAM does something a ROM can't.

{{ mem.name }} {{ mem.note }}

Footprints are the PR's memorySize: max(5, label+4) × 3 for ROM, × 9 for RAM, ports on the and_gate odd-row pattern, out at the middle row. The renderer needs addr and the addressed word at draw time — inputValues[0] already carries the address; the word is outputValue for both modes since reads are asynchronous. The write flash needs one extra bit from the runtime: whether the last step committed a write.
