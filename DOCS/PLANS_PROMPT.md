# Plan Prompt — Agent-Driven Playground

## What Is Being Built

Make `/playground` operable by browser-integrated WebMCP agents and external coding agents such as OpenCode and Claude Code. An agent should be able to discover the open project, consult the circ language reference and examples, write `.circ` code, compile it, diagnose and repair errors, and verify its behavior in the playground the human is watching. The user approved both agent environments and the full operational scope. External agents may require an existing browser-control tool configured locally. The site remains statically deployed: project state, compilation, simulation, and reference lookup run in the browser, with no added application backend, relay service, or custom HTTP/WebSocket bridge server.

Completion means both access paths can create and open projects; read, write, rename, and delete files; select the entry file; compile and read structured diagnostics and revision-aware status; drive inputs, read outputs, reset, inspect and edit ROM/RAM, and load memory images; inspect schematics and truth tables; change relevant settings and views; and produce share links and exports. A first-class `circ_help` tool searches reference sections, retrieves diagnostic guidance, and returns complete examples with sibling files and required memory preloads. Every live mutation is reflected in the existing UI and, for simulation actions, its console record. Results identify the project, source/build revision, and session they describe so a last-good artifact cannot be mistaken for the current source.

The initiative builds on the existing TypeScript project model, compiler worker, editor handle, and shared `SimSession`. Extract a typed controller and tool registry incrementally from `site/src/components/Playground.astro`; the UI, native WebMCP adapter, and external browser-tool access path call the same application operations. Delivery is proven through actual tool calls in a supported browser-integrated agent and in external coding agents, including author/repair/verify workflows, concurrent human edits, multi-file entry changes, memory preloads, and reload recovery. Record the tested browser, agent, and connection-tool versions; mocked registration and direct controller tests alone do not satisfy the connection acceptance gate.

## Tech Stack

- Worktree: `worktrees/webmcp-playground`, branch `webmcp-playground`; planning baseline `7faa57a`, with no active plan bundle before this file.
- Site: Astro 5, TypeScript, plain browser DOM APIs, and Bun; `site/package.json` and `site/bun.lock` define dependencies and commands. Node is pinned by `site/.node-version` to 22.19.0.
- Editor: CodeMirror 6 through the exact-pinned packages and dynamically imported `site/src/scripts/circ-editor.ts`; the textarea remains the fallback surface.
- Compiler: committed `site/public/wasm/libcirc.wasm` and `libcirc.manifest.json`, owned by `site/src/workers/libcirc.worker.ts` and accessed through `LibcircClient`. The manifest currently reports circ 0.0.3, compiler revision `e8869c8`, and topology/full version 3; runtime handshake data is authoritative.
- Simulation/rendering: `site/src/scripts/sim-session.ts` over the pinned `circ-renderer#2d973b4` (`2.3.0-alpha.4`); canvas, Data, memory, and console share one live session.
- Storage/interchange: one `localStorage['circ.playground.v1']` envelope, schema version 2; source uses the existing `// <name>.circ` marker format and fragment-based share codec.
- Agent access: native imperative WebMCP where supported; an explicitly documented, schema-bearing page tool registry callable through existing external browser-control tooling. Phase 0 verifies the available browser API and connection mechanism rather than assuming compatibility.
- Knowledge: canonical `DOCS/` references, `site/src/content/examples.ts`, and `site/src/content/tour.ts`; generated static assets extending the existing reference/LLM-mirror build pipeline. Search executes locally and loads its corpus on demand.
- Tests: `bun test`, `astro check` through `bun --bun run typecheck`, built-island happy-dom tests, real `libcirc.wasm`/runtime tests, and real-browser agent workflows. The existing bundle gate is `bun run bundle` after a site build.
- Deployment: the existing static Astro site and bun-only site deployment; existing WASM artifacts are consumed as committed. Zig 0.15.x is needed only for changes that require compiler/runtime regeneration.

## Architectural Constraints

- **One application contract, two agent access paths.** Define typed inputs and JSON-safe results in importable TypeScript modules. Native WebMCP registration and a documented browser-evaluation entry point expose the same tool definitions and handlers. The external registry supports tool discovery and invocation even when native WebMCP is unavailable. Existing browser-control tooling connects an external agent to the tab; this initiative does not create a new bridge service. Keep browser API detection, registration, and teardown inside a small adapter.
- **Prove connectivity first.** Phase 0 records a working native browser/agent combination and existing external connection tooling, including installation/launch instructions and tab selection. Verify discovery and a real read-only call from both OpenCode and Claude Code using that tooling. If a required path cannot work within the serverless constraint, stop and bring the concrete blocker to the human before implementing dependent phases. Consult the current WebMCP specification and the selected implementation; the explainer inspected during planning uses `document.modelContext`, while earlier examples use different APIs. Do not treat either spelling as a compatibility guarantee.
- **Shared controller and visible state.** Extract only the orchestration needed by each shipping phase. Project/editor operations, compiler operations, and session operations flow through that controller; reading state must not scrape rendered text, and writing state must not simulate keystrokes or modify localStorage behind the editor. Preserve the existing lazy-loading and textarea paths. The test-only `el.__playground` object is not the public tool contract. See `DOCS/decisions/playground.md` and `DOCS/decisions/playground-bench.md`.
- **Revision-aware operations.** Track document/page lifetime, project identity, source revision, relevant configuration revision, analysis/build request identity, and live session identity. Capture files, entry file, options, and preload provenance together before asynchronous work. Results distinguish queued/running, succeeded, diagnostics/refused, failed, and superseded work. Last-good output carries its own provenance and freshness; source equality and artifact-byte equality are different facts. Reset/replacement invalidates the corresponding session identity. A successful byte-identical compile must still record which source revision was validated.
- **Concurrent edits are explicit.** Mutations of an existing project carry the expected project/revision and validate before changing anything. Batch file changes are applied as one validated model update, scheduling one coherent pipeline update; a conflict returns the actual revision and an actionable result. A build completing after a human edit answers for its captured revision and cannot claim that the current source succeeded. Session mutations check the expected session and artifact/configuration provenance after asynchronous preparation. Serialize conflicting asynchronous mutations, including reset, and keep the UI's operation path consistent with the same rules.
- **File identity and entry selection follow the bench.** Preserve `splitFiles`, `joinFiles`, `isFileName`, and `joinConflicts`; structured tool arguments may use named-file arrays but persistence and interchange retain the marker format. The active editor file is the compilation entry point, with every sibling retained in the overlay. The last file remains the default on first open and interchange. Selecting an explicit tool target uses the same visible file-selection path, immediately invalidating unrelated outputs. Reading an inactive file alone does not select it. Do not introduce a second persistent root pointer. See `DOCS/decisions/playground-bench.md`, “The active editor file is the playground entry point.”
- **Edits preserve user work and editor history.** Ordinary source updates use editor transactions and preserve per-file undo/selection; replacing the entire document registry is reserved for the operations that actually replace a project. Shipped examples/tour steps fork through the existing scratch path on first edit; the result returns the new project ID. File/project rename, duplicate, and delete carry associated source images through the existing ownership rules. Validation, persistence limits, evictions, and save failures are reported as structured outcomes. Keep the existing 16-project, 32 KiB source, and 256 KiB envelope limits and the version-2 migration contract. See `DOCS/decisions/playground.md`, “One editor state per file is what makes undo per-file,” and `DOCS/decisions/playground-bench.md`, “The envelope moves to version 2 by migration, once.”
- **Compiler ownership and diagnostics stay shared.** Reuse the worker/client and per-operation settings projection; the compiler WASM stays in its worker. Add explicit awaitable build outcomes to the existing orchestration rather than a second agent-only compiler pipeline. Both analysis and status-1 compile diagnostics use their own request's file mapping. Tool-facing ranges declare file-local line/column bases and encoding, with byte-to-UTF-16 conversion shared with `circ-diagnostics.ts`. Syntax errors, compiler diagnostic codes, library refusal/status codes, and tool transport failures remain distinguishable. See `DOCS/decisions/libcirc.md`, `DOCS/libcirc-api.md`, and `DOCS/analyze-api.md`.
- **Knowledge comes from shipped sources.** `circ_help` provides search, read-by-ID, and complete-example retrieval. Generate section records from `DOCS/language.md`, `DOCS/getting-started.md`, and the diagnostic material in `DOCS/circuit-format.md`, checking diagnostic IDs against `lib/validator/codes.zig`; include `DOCS/sim-protocol.md` for playground driving help. Generate examples from `examples.ts` and the retained tour content, not handwritten copies. Return stable IDs, source paths/URLs/anchors, compiler/grammar and corpus identity, excerpts or full requested sections, and bounded results. Example retrieval includes named files, entry file, description, and memory images. Start with deterministic lexical search, boosting exact diagnostic/construct matches; no hosted search, embeddings service, or mandatory whole-library response. Exact tool schemas and section IDs are phase-spec details.
- **Knowledge is validated, not presumed current.** The index and public Markdown twins derive from the same canonical content. The build must not label mismatched corpus/compiler identities as matching. Compile complete returned example projects against the shipped `libcirc.wasm` and exercise representative behaviors/preloads; reference sections that intentionally demonstrate errors are not positive compile fixtures. Validate generated IDs, links, and coverage, and remove obsolete generated entries through an owned manifest so stale knowledge does not survive regeneration.
- **One live simulation session.** Pin and live-memory mutations go through `SimSession`, preserving event-driven updates to the canvas, Data, memory views, and console. Pin lookup uses declared names; values and defined-bit masks cross the tool boundary as lossless strings, never JSON numbers for arbitrary u64 data. Tool errors preserve the existing session codes. Ordered assignments retain the session's settle-after-each-assignment semantics; a batch is not an atomic simultaneous pin drive. The page's initial boot is low, while reset leaves pins undefined and reapplies preloads. See `DOCS/decisions/playground.md`, “One simulation session, and every face drives through it,” and `DOCS/sim-protocol.md`.
- **Verification is isolated and bounded.** User-supplied verification vectors run in a disposable session from a known artifact and explicit initialization/preload configuration; they do not alter live pins, RAM, or the console. Stateful scenarios retain state between their ordered steps; independent cases explicitly reset. Results carry expected/actual values and masks, case/step IDs, provenance, and failures. Bound cases, output size, and enumeration before execution. Long-running operations must yield where feasible and report honest timeout/cancellation semantics; terminating a wait is not proof that synchronous WASM stopped.
- **Memory ownership is explicit.** Discover root ROM/RAM with their compiled shape; root live operations use the existing session API. Source ROM preloads are addressed by project/file/declaration, with imported instances receiving independent copies through `ImportedImages`. Inspection distinguishes an imported instance's runtime identity from its owning declaration. Avoid ambiguous bare-name writes to nested memories. Keep live RAM edits separate from persisted source ROM image edits, and report which form an operation performed. Runtime-instance editing beyond the session's current root API requires an explicit phase-spec design that preserves the shared-session event path. See `DOCS/decisions/playground-bench.md`, “ROM images belong to source declarations.”
- **Truth and inspection report their scope.** Reuse the existing compiler/scratch Truth paths, one cap setting, the RAM refusal, and source-image handling. Results say whether the table is exhaustive or filtered and identify held inputs, unknown inputs, input-bit count, row count, and provenance. Paged output does not authorize unbounded computation. Schematic text and topology data come from compiler/runtime data, with explicit expansion settings and bounded inspection; source highlighting uses the existing top-level name/kind join. See `DOCS/decisions/playground-bench.md`, “Over the cap, the Truth view shows the rows the pins select.”
- **Share and export tell the truth about contents.** Reuse the fragment codec, cap, early scrub, artifact download, and memory-image export paths. Return a share URL or an explicit over-cap result without depending on clipboard permissions. Source links and WASM artifacts do not contain memory image contents or a live RAM snapshot; report those omissions and export required images separately when requested. Declare what a source, WASM, memory, or transcript export contains, and bind generated exports to their source/artifact/session provenance. See `DOCS/decisions/playground.md`, “A share link carries the source in the fragment, under two keys,” and the bench's source-image decision.
- **Static deployment and accurate integration documentation.** Compilation, simulation, and retrieval require only the static site and its assets. Existing locally configured agent/browser tooling is the accepted connection dependency. Document that requested tool results are returned to the connected agent, distinguishing local computation from the agent's own handling of source/result data; page integration copy must accurately describe this behavior. Expose app-level operations and capability metadata, with consistent argument validation and JSON-safe outcomes across both adapters.
- **Dependencies, budgets, and shared layers remain deliberate.** Preserve the Astro/TypeScript structure, exact editor pins, renderer pin, and per-page budget from `DOCS/decisions/playground.md` and `DOCS/decisions/libcirc.md`. Lazy-load knowledge and heavy UI/runtime modules. The budget currently gates 10,240 gzip bytes by default and `/playground` at 368,640 raw / 122,880 gzip; increases require a measured, reviewed decision. Compiler/runtime/renderer changes must be justified by a concrete unmet operation and follow their own build, compatibility, and artifact rules; the baseline plan uses their existing APIs. Architectural decisions exercised by a phase land in `DOCS/decisions/` with that phase.

| 4 | Drive and verify circuits | Shared-session pin/read/reset and ROM/RAM inspection/edit/preload tools plus bounded isolated vector/scenario verification, proven by a half-adder truth-vector check and a RAM clock/write/read/reset scenario with identical UI/console state. |

Phases are ordered by dependency, not by priority. Each phase must be fully shippable before the next begins. Phases 0–4 provide the author/help/compile/repair/verify loop; completion of this initiative includes Phases 5 and 6 as the human approved the full scope. Each phase includes its relevant automated and browser checks; Phase 6 is the integrated acceptance pass, not the first browser test.

The tool families above define outcomes, not a requirement to register one giant action dispatcher or dozens of overlapping tools. Phase specifications assign semantic tool names, argument schemas, response limits, and context-dependent registration. `circ_help` is the named language-assistance entry point. Keep discovery useful when no project or compiled session exists, and expose capability/refusal reasons consistently as state changes.

## Working Loop

The execution agent follows this loop every session without exception:

### On Cold Start

1. Read this file (`DOCS/PLANS_PROMPT.md`) in full.
2. Read `DOCS/STATUS.md` (if it exists). The latest entry defines what was last shipped and what comes next.
3. Run `git log --oneline -10` and `git status`. If STATUS claims a slice is committed but it does not appear in `git log`, the human has not committed yet — **do not begin a new slice**. Stop and say so.
4. Read the active phase plan (`DOCS/PLANS/PHASE_<N>_<name>.md`) for the current phase. If it does not exist, stop and request the phase-planning session using `DOCS/prompts/PHASE_DEEP_PLANNER.md`; this macroplan does not substitute for a reviewed slice specification. Initially Phase 0 is next, and no implementation STATUS entry exists.
5. Implement the next slice per the phase plan. Do not start a second slice until the first is reviewed and committed. Read `CLAUDE.md`, the architectural decisions relevant to that slice, and the actual source before changing its behavior; later bench decisions supersede older playground decisions where explicitly amended.

### Each Slice

1. Implement the full slice as specified. Do not stop mid-slice. Include the API/usage documentation and architectural decisions that the slice exercises; record newly discovered traps below.
2. Run the project's test command for the affected modules. Do not ship a slice that breaks the suite. For site implementation slices, from `site/`, run `bun --bun run typecheck`, then `bun --bun run build`, then `bun test` and `bun run bundle`; the build must precede the suite so built-island tests do not skip or read an old `dist/`. Record exact commands and results. Run the phase's real-browser checks through its public tool access paths. If a check is unavailable, record the blocker and do not describe the slice/phase's acceptance as passed. If a justified change touches Zig, follow `CLAUDE.md` and run `zig build test-all` from the repository root; renderer changes require that repository's own tests/typecheck and the site's pin/compatibility checks.
3. Append a STATUS entry (template below). Include exercised browser/agent/connection-tool versions and tool-call evidence for integration slices. State the next slice only after all required acceptance checks for this slice are complete; otherwise name the outstanding work.
4. Stage the slice's files (`git add <files>`). Inspect `git status`, `git diff`, and `git diff --cached`; stage by explicit path and include only the intended slice.
5. Display the proposed commit message and **stop**. Wait for explicit human approval before running `git commit`. Do not begin the next slice until the commit is confirmed and made. Titles follow `CLAUDE.md`'s Conventional Commits style, without phase/slice prefixes or co-author trailers.

### Git Rules

- Read-only git commands (`status`, `log`, `diff`) are encouraged for situational awareness.
- **Committing:** At the end of a slice — and only at the end of a slice — the agent stages the slice's files (`git add <files>`), then displays the full proposed commit message to the human and waits for explicit approval before running `git commit`. Staging first lets the human inspect the diff in any git client before approving. Do not commit without that confirmation.
- Do **not** push, force-push, amend, rebase, reset, delete branches, or run any other write `git` or `gh` command under any circumstances. The explicitly described staging and approved slice commit are the only exceptions in this working loop.

## Recurring Traps

- **Browser registration is not external-agent connectivity.** WebMCP availability and tool discovery vary by browser/agent version. A browser-control tool may execute page JavaScript without automatically importing page tool schemas into the agent's tool list. Phase 0 must demonstrate the actual discovery/call workflow and document it for both external clients. A successful mock or DevTools-console call alone proves neither agent path.
- **The existing debug hook is mutable test scaffolding.** `Playground.astro` exposes state and callbacks on `el.__playground` for built-island tests. Do not publish that object or depend on its private shape as the external contract.
- **Old decisions can be historical.** `DOCS/decisions/playground-bench.md` supersedes the last-file-only runtime root and session-only ROM image policies in earlier playground records. Active file is the runtime root; image ownership is project/file/declaration. Follow current source and explicit amendments.
- **Debounce sequence is not source revision.** `Stage` claims a sequence when a timer fires. An older result can arrive after a body edit but before the next debounce fires. Capture request snapshots before awaits and compare their revisions when answering tools; preserve the UI's last-good display while reporting its age accurately. A settled promise is not necessarily a successful current build.
- **Build and analysis can finish independently.** Both produce diagnostics, and compile status 1 carries its own `files[]`. A current analysis must not be paired with an older artifact's file IDs. Identical artifact bytes can still require a session replacement when imported-image file-ID provenance changes.
- **Editor setters do not all emit change events.** `EditorHandle.setDoc` deliberately suppresses `onChange`; an agent write must explicitly update the project model, persistence, revisions, and pipeline through the controller. Resetting all documents for an ordinary edit destroys per-file history. UTF-8 byte ranges and UTF-16 editor offsets are not interchangeable.
- **Marker text has representability limits.** Duplicate names, illegal names, blank non-last bodies, and marker-looking lines after code can break round trips. Use `joinConflicts` before accepting a structured file batch, and return the conflicting file/reason without partial mutation.
- **Settings are not one interchangeable options bag.** Store fields are camelCase; compiler options are per-operation snake_case. Unknown options are bad requests. Preserve the shared projection, and verify that warnings-as-errors is actually applied to build/refusal paths rather than inferred from analysis severities.
- **Session identity matters even when pin shape is unchanged.** Same-shaped recompiles can leave handlers bound to destroyed runtimes. An asynchronous reset or load must not land after the user switched projects or artifacts. Include reset, replacement, and tool-call concurrency in the phase's lifecycle tests.
- **Boot-low and reset-floating produce different RAM edges.** A first `clk=1` after initial low boot is a rising edge; after reset it is not. `eval` settles each assignment in order. Verification scenarios must declare initialization and preserve assignment order.
- **Every simulation action has one record.** The console currently suppresses session echoes while its own command is busy. Introducing another asynchronous caller requires checking interleavings so agent actions are neither lost nor double-logged. Emit through the shared session; never rerun an action just to obtain a transcript line.
- **Memory names are not globally unique.** Two source files can declare the same ROM name, and one imported source can have multiple runtime instances. Root `SimSession.mems` does not enumerate nested instances. Source-preload edits and runtime-instance edits need different identities and lifetime semantics.
- **Images are needed to reproduce memory examples.** The lightweight playground catalogue omits some metadata present in `Example`, including memory images. Generate help examples from the full content records. Share links, compiled WASM, and copied console scripts do not package those images; exporting source alone must not claim a memory scenario is reproducible.
- **The mirror does not currently clean up removed twins.** `DOCS/archive/plan-playground.md` records the stale `/examples.md` problem. The new generated corpus needs explicit ownership/cleanup and must not delete unrelated static assets. `DOCS/sim-protocol.md` is currently outside the site's five-document mirror list, so any new public citation needs a generated destination that actually exists.
- **Content IDs and compiler identity need care.** Tour IDs are positional today. Give retrieval records a deliberate stability policy. A committed WASM manifest names the compiler commit at build time, normally before the commit that adds the artifact; do not equate current Git HEAD with the binary's own revision. Report corpus and compiler identities separately.
- **Some reference material describes known compiler quirks.** The archives record anonymous-position builtin specialization failures and parser keyword-prefix behavior. Reference examples intentionally showing errors must remain labeled as such; assistance must not present a known failing construct as a verified recipe.
- **Truth response limits do not bound enumeration.** Worker compiler calls are synchronous and cannot currently be aborted. The scratch Truth path enumerates synchronously on the main thread; prior measurements did not establish acceptable cost at the full cap. Bound computation before starting, and verify responsiveness where agent tools make repeated enumeration practical. Current partial-bus filtering treats an entire partly unknown input as unknown; returned scope must say so.
- **Read-only tools should stay cheap.** Status and help discovery must not initialize the compiler or simulator merely to describe them. Session creation and fresh analysis/build are explicit operations with reported lifecycle; returning an empty pin list must not imply the compiled circuit has no pins when no session exists yet.
- **Static-site lifecycle includes restoration.** Tool registration must tolerate initialization, late editor loading, pagehide/reload, and remount without duplicate handlers or references to destroyed state. Tool results must identify the page lifetime so a revision from a previous load cannot match accidentally.
- **Browser checks were historically deferred.** `DOCS/archive/plan-playground.md` and `plan-playground-bench.md` carry unperformed browser checks. `island-smoke.test.ts` runs built HTML/scripts but cannot exercise a normal browser worker and native WebMCP stack; it also skips without `dist/`. Do not inherit a historical pass claim or count skipped checks as coverage.
- **Do not race the dev server with a site build.** Both run generators that write `public/`. Stop the dev server before `bun --bun run build`, then use the built-site preview for browser acceptance. The archived local Rosetta/Node Rollup issue is why the documented build/typecheck commands use `bun --bun`.
- **Planning is not implementation.** This file was generated after the human approved the macro-planning session. Generate one reviewed phase specification at a time using `DOCS/prompts/PHASE_DEEP_PLANNER.md`; do not create implementation STATUS entries, execute slices, or archive the initiative merely because the macroplan exists.
